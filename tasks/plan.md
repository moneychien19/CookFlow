# Implementation Plan: CookFlow

## Overview

Build CookFlow as described in [SPEC.md](../SPEC.md): a Next.js app where a cook keeps a pantry in practical units, gets single-meal suggestions, generates a 2–5 meal plan that uses opened and expiring items first, sees hard-to-use leftovers before → after, and marks meals cooked so the pantry updates. Only the **In** list of SPEC §1 is in scope.

The repo currently holds only docs (SPEC, DESIGN, README, CLAUDE). Everything below is new code.

## Architecture decisions

- **Drizzle + Neon serverless driver** (CLAUDE.md default; SPEC allows Drizzle or Prisma). Migrations generated by drizzle-kit and committed.
- **Planner first, as a pure module.** `src/lib/planner` has no DB or Next.js imports and works in integer hundredths. It is the highest-value and most precisely specified part, so it goes early and gets fully tested against small factory fixtures before any UI exists.
- **Dev seed before real seed.** A hand-written `seed/dev-recipes.json` (~10 recipes, same zod schema as the real one) unblocks every page. The TheMealDB import and hand review run in parallel and replace it later. This keeps the slow, manual part of the project off the critical path.
- **Shared demo account.** SPEC §7a #8 requires core features to work without signing in. One seeded demo user with a fixed id; a visitor without a session who clicks "Try the demo" acts as that user (a `cookflow-demo` cookie the server checks, no Credentials provider). `requireUserId()` returns the session user, else the demo user if the cookie is set, else redirects to `/`. Auth.js keeps its default database sessions. All demo visitors share one pantry and plan list; "Load sample pantry" resets it.
- **Sign-in providers:** GitHub and Google.
- **Skipping a meal** is in scope: a plan item can be set to `skipped` (no pantry change), and the "next meal" is the first `planned` item.
- **One shared scoring path.** `/suggest` is the planner's scoring function run once (N = 1, no depletion); `/plan/new` runs the greedy loop. No second ranking implementation.
- **Leftovers metric = count of hard-to-use items** (non-staple, `0 < qty < 1`, unit in whole/pack/bunch). Snapshotted on `meal_plans` at generation time.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Seed normalization is slow and manual | High | Dev seed unblocks everything; real seed swaps in later; drop recipes rather than force-map them |
| Shared demo pantry gets emptied or cluttered by other visitors | Med | "Load sample pantry" resets it in one click; landing page says the demo is shared |
| Demo cookie mistaken for real auth | Med | Demo cookie only ever maps to the fixed demo user id; `requireUserId()` is the single place it's read; test that it can't reach another user's data |
| Float drift in quantities causes wrong "partial" counts | Med | Hundredths internally; explicit `1 - 0.5 - 0.5` test in T5 |
| Greedy picks feel wrong on real pantries | Med | Tune weights at Checkpoint A with 3–4 fixture pantries; suboptimal case documented, not fixed |
| `FOR UPDATE` needs a real transaction; Neon HTTP driver doesn't do interactive transactions | Med | Use the Neon WebSocket `Pool` driver for transactional writes (T7) |
| DB tests need a live Postgres in CI | Low | Neon branch per CI run, or a Postgres service container in GitHub Actions |
